# Stage 2 — Collector

Added the first four shared records to `common` — VehiclePosition, TripUpdate, StopTimeUpdate and ServiceAlert — and built the collector service around an abstract `FeedPoller<T>` whose `pollOnce()` is final: fetch, archive, decode, skip-if-unchanged, map, publish, written once so no subclass can reorder it. Each feed is one subclass supplying only its url, name, topic, mapper and message key, on its own `@Scheduled(fixedRate)` with a three-thread scheduler so one slow feed cannot delay the others.

Designed the records against real captured snapshots rather than the GTFS-Realtime spec, which changed the design three times. 380 of 886 trip updates carried no `trip.trip_id` at all — they use `modified_trip` — so the mapper resolves the id from `trip.trip_id`, then `trip_properties.trip_id`, then `modified_trip.affected_trip_id`, and all 886 resolved. The feed's `entity.id` is deliberately never used as an identifier: one id appeared three times in a single snapshot, and the third occurrence described a different trip.

Every optional field is read through `hasX()` and stored as null when absent, which is why the records use boxed types. Protobuf returns 0 for an absent number, so a bus that never reported its speed would otherwise be indistinguishable from one standing still. `currentStatus` was present on 11 of 69 vehicles and `directionId` on 34, so absence is normal rather than exceptional.

The skip-if-unchanged rule started as a comparison of the feed header timestamp and was wrong: Stage 1 had already shown the header advances on every poll, so it would never have skipped anything — the alerts feed alone would have republished ~475 records every 20 seconds, about two million messages a day describing a handful of disruptions. Replaced with a SHA-256 over the decoded entities. Measured over 180 consecutive snapshots per feed: content changed on 92.7% of polls for vehicle positions and trip updates, and **0%** for alerts. The entities are hashed individually rather than by clearing the header, because `header` is a required field and a message without one cannot be serialised at all.

Two platform and packaging traps cost real time and are worth remembering. `spring-kafka` alone provides the classes but not Boot's auto-configuration, so nothing read the `spring.kafka.*` configuration and no `KafkaTemplate` bean existed — `spring-boot-starter-kafka` is what wires it. And `Files.move` with `ATOMIC_MOVE` silently replaces an existing target on Windows, so the archiver's same-second collision check never fired; the name is now reserved with `Files.createFile`, which fails atomically on every platform. A third: `NoSuchMethodError` from a stale `common` jar in the local repository after changing a record — an `Error`, not an `Exception`, which is why it escaped the poller's `catch (Exception)`.

Measured the Stage 6 contingency while the archive was to hand: the agency's own `delay` field appears on **34.8%** of 4.7M stop-time updates and swings from 0% between 02:00 and 04:00 to 70% late evening, while `time` minus `scheduled_time` is derivable at **93–97% in every hour**. The published-delay fallback therefore has coverage that depends on the clock, which is worse than no fallback because the bias is invisible in the output.

The collector archives to `data/dev-archive`, not `data/raw`, and stays that way through November: `scripts/save_feeds.py` remains the sole writer of the dataset the findings depend on. The collector only runs when started by hand, so letting it own the archive would put holes in that dataset. An operational choice, deliberately not a decision record.

The same collision defect exists in `save_feeds.py`, which also names files `HHMMSS.pb.gz` and moves with `os.replace`. It never fired: two savers ran simultaneously for nine hours on 25 September, and their fixed grids sat at constant offsets of 9s and 13s, so no two writes ever shared a filename — 358 files and 358 distinct names in the sampled hour. Two fixed-grid writers either collide on every poll or on none, depending on phase.

31 tests, all against real `.pb.gz` fixtures from the archive: the three mappers, the content hash, the archiver, and the poller's failure behaviour — a failed fetch, an HTTP error and malformed bytes each leave the scheduled task alive and publish nothing, while still archiving the bytes.
